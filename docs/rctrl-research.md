# 다음 버전 연구: Copilot 키를 RCtrl로 사용하기

상태: RCtrl 유지 입력은 설계 조사 단계입니다. 0.2.0에는 별도 범위로 Windows 키를 한 번 누르는 모드를 구현했습니다.

이 문서는 Banpilot 0.1.0을 기준으로 시작한 연구 기록입니다. 초기 조사에서는 기존 앱의 무동작 기능과 패키지 버전을 유지했습니다. 이후 0.2.0의 구현 및 검증 상태는 [README](../README.md)를 참고하십시오. 연구만으로 시작 프로그램, 드라이버, 인증서 신뢰 설정을 변경하지 않습니다.

## 목표

Copilot 키를 누르고 있는 동안 RCtrl이 눌린 상태를 유지하고, 키를 떼면 RCtrl을 해제하는 동작을 검토합니다. `Copilot+C`가 `RCtrl+C`로 동작해야 합니다. 한 번의 RCtrl 누름/해제 입력을 생성하는 것은 이 목표를 충족하지 않습니다.

RCtrl을 우선 검토하고 RAlt는 후속 후보로 둡니다. RAlt는 사용 중인 키보드 레이아웃 및 입력기의 동작을 추가 검증해야 합니다. 설정 화면을 먼저 만들기보다 실제 입력 처리가 가능한지부터 확인합니다.

## 현재 확인한 근거

- 현재 앱은 Windows의 `com.microsoft.windows.copilotkeyprovider` 확장에 등록한 실행 대상입니다. 이 확장 자체는 물리 키의 누름/해제를 전달하는 인터페이스를 문서화하지 않습니다.
- 2026-10-19 현재 PC에서 관찰한 순서는 `LWin DOWN → LShift DOWN → F23 DOWN`, 해제 순서는 `F23 UP → LShift UP → LWin UP`입니다.
- 약 1.19초 누름에서 F23 DOWN이 21회 관찰됐고 LWin·LShift DOWN도 반복됐습니다. 최초 입력만 처리해서는 충분하지 않습니다.
- 이 관찰은 사용자 공간 키보드 훅의 결과입니다. 모든 기기·키보드·펌웨어가 같은 입력을 보낸다고 가정하지 않습니다. 물리 장치별 식별은 이 기록에 포함되지 않습니다.
- 이 PC의 Windows 설정에서 직접 확인한 선택지는 검색, Copilot, 앱 열기였습니다. RCtrl을 제공하는 Windows 버전 또는 제조사 설정이 있다면 그 경로를 별도로 확인합니다.

## 구현 후보와 제약

| 후보 | 판단 | 다음 확인 |
| --- | --- | --- |
| 기존 앱 실행 후 RCtrl 입력 합성 | 누르고 있기와 해제를 보장하지 못하므로 단독 해법으로 채택하지 않음 | 앱 활성화 시점과 물리 키 이벤트는 서로 다름 |
| 사용자 공간의 상주 입력 처리 | 첫 구현 실험 후보. 상주 프로그램을 허용한다는 제품 결정이 필요함 | 일반 Win·Shift와 Copilot 입력 구분, 원래 입력 차단, 해제 보장, 관리자 앱과의 동작 |
| 키보드 필터 드라이버 | 후순위 | 드라이버 서명·배포, 장치별 입력 형태, 부팅·절전·분리 및 복구 검증 |
| Windows/제조사의 기본 키 변환 | 지원 환경에서는 우선 검토 | 현재 빌드와 키보드에서 지원되는지 확인 |

`SendInput`은 이미 눌린 키 상태를 초기화하지 않으며, 현재 눌린 Win·Shift가 합성 입력에 영향을 줄 수 있습니다. 또한 더 높은 무결성 수준의 앱으로 입력을 주입하는 데 제한이 있습니다. 키 변환이 모든 앱에서 동작한다고 약속하지 않습니다.

일반 키보드의 Win·Shift 입력을 일괄 삭제하거나 짧은 시간 간격만으로 Copilot 입력이라고 확정하면 정상 단축키를 훼손할 수 있습니다. 타이밍 추정만으로 범용 지원을 선언하지 않습니다.

## 첫 실험 순서

1. 자동 종료되는 관찰 도구로 짧게 누름, 길게 누름, 연타, Win·Shift를 먼저 누른 경우의 입력 순서를 비교합니다. 일반 문자 내용이나 전체 타이핑을 저장하지 않습니다.
2. 익명화한 제한된 이벤트 시퀀스로 상태 전이를 설계합니다. 일반 Win·Shift를 보존할 수 없으면 해당 접근의 한계로 기록합니다.
3. RCtrl 누름·반복·해제 처리를 별도 실험 프로그램으로 구현합니다. 자동 시작이나 드라이버 설치를 넣지 않고 명시적으로 실행·종료합니다.
4. 아래 실기 기준을 통과한 뒤에만 사용자용 선택 화면과 패키지 통합을 검토합니다.

## 통과 기준

- 짧게 누르기, 길게 누르기, 연타에서 Copilot 창이 열리지 않는다.
- 누르는 동안 `RCtrl+C`, `RCtrl+V`, `RCtrl+A`가 동작하고, 해제 후 Ctrl 상태가 남지 않는다.
- 원래 Win·Shift·Ctrl 및 한영 전환, 다른 키보드의 입력이 정상이다.
- Win 또는 Shift를 먼저 누른 상태에서도 오인식이나 키 고착이 없다.
- 일반 앱과 관리자 권한 앱의 결과를 구분해 기록한다.
- 프로그램 정상 종료, 오류, 절전·복귀, 키보드 분리·재연결에 대한 복구 동작을 검증한다.
- 지원하지 못하는 환경은 명시하고, 현재의 무동작 모드로 복구할 수 있다.

## 2026-10-19 구체 설계 초안

### 길게 누를 때 앱 실행 횟수 실측

2026-10-19 현재 PC에서 Banpilot을 Copilot 키 실행 대상으로 둔 상태로 한 번 길게 누르는 실험을 수행했습니다.

| 관찰 항목 | 결과 |
| --- | --- |
| F23 누름부터 해제까지 | 약 10.498초 |
| F23 DOWN 이벤트 | 290회 (최초 누름 및 반복 입력 포함) |
| F23 UP 이벤트 | 1회 |
| `Banpilot.exe` 프로세스 시작 | 1회 |

프로세스 관찰에는 `Win32_ProcessStartTrace`를 사용했습니다. 관찰 시작 전 짧게 실행되고 종료하는 Banpilot 프로세스를 실제로 포착하는 자체 검사를 통과했으며, 그 자체 검사 프로세스는 실험 횟수에서 제외했습니다. 키 해제 후에도 관찰한 뒤 종료했습니다.

이 실험에서는 키 입력의 반복이 앱 프로세스의 반복 실행으로 이어지지 않았습니다. Windows의 모든 버전에서 같은 실행 정책을 사용한다거나 앱 실행 시점이 항상 누름/해제 중 특정 시점이라고 일반화하지 않습니다. 앱 활성화 횟수를 물리 키 반복 입력이나 키 해제 신호로 사용할 수 있다는 근거도 되지 않습니다.

아래는 구현 결정이 아니라 사용자 공간 변환의 가능성을 검증하기 위한 제안입니다. 0.1.0의 비상주 동작을 유지하면서 RCtrl 변환 모드에만 별도 실행 프로세스를 사용하는 방향입니다. 상주 여부는 사용자에게 명확히 표시해야 합니다.

### 실행 구조

| 구성 | 책임 | 수명 |
| --- | --- | --- |
| 기존 `Banpilot.exe` | Copilot 실행 대상으로 남아 즉시 종료 | 호출될 때만 실행 |
| 변환 프로세스 | 입력 판별, 원래 조합 억제, RCtrl 누름/해제 합성 | 변환을 켠 동안 실행 |
| 설정 화면 | 무동작/RCtrl 선택, 변환 시작·중지, 현재 상태 표시 | 사용자가 설정을 열 때 실행 |

첫 실험에는 설정 화면과 자동 시작을 만들지 않습니다. 변환 프로세스를 수동으로 실행하고 종료하는 것부터 검증합니다. 구현 언어는 기존 C# 및 Win32 호출을 우선 후보로 삼아 기존 빌드 체계를 재사용합니다.

### 핵심 난점: F23을 보기 전에는 Copilot인지 알 수 없음

관찰한 짧은 누름에서 LWin·LShift·F23은 같은 Windows 메시지 시간값을 가졌습니다. 이는 해당 입력의 관찰 특성이며, 같은 시간값이 물리적인 Copilot 키의 고유 식별자라는 뜻은 아닙니다.

- Win·Shift를 즉시 통과시키면 F23을 확인할 때 이미 원래 입력이 전달됐을 수 있습니다.
- Win·Shift를 잠시 보류하면 Copilot 조합을 제거할 기회가 생기지만 일반 키 입력에 지연이 생깁니다.
- 보류한 입력을 다시 보내는 것은 원래 입력의 단순 반환이 아니라 합성 입력입니다. 순서, 보안 수준, 대상 앱의 처리 차이를 검증해야 합니다.
- 훅에서 보이는 이벤트가 완전히 동일하면 물리 Copilot과 사람이 누른 같은 조합을 확정적으로 구분할 수 없습니다. 같은 장치에서 나온 경우 Raw Input의 장치 식별만으로도 해결되지 않습니다.

따라서 고정된 10ms/30ms 같은 임계값을 먼저 확정하지 않습니다. 실제 입력 분포, 일반 Win 단축키 지연, 오탐을 측정한 뒤 지원 범위와 한계를 결정합니다.

### 상태 전이 후보

| 상태 | 처리 방향 |
| --- | --- |
| 대기 | 일반 입력은 전달. 후보가 될 수 있는 수정 키 입력만 제한적으로 보류 |
| 후보 수집 | 짧고 제한된 버퍼에서 패턴 검사. 다른 입력이 끼면 순서대로 복원하는 방안 검증 |
| RCtrl 활성 | 지원하는 패턴으로 판단되면 RCtrl DOWN 한 번 전송. 해당 조합의 반복 DOWN은 억제하고 일반 문자는 전달 |
| 해제 정리 | F23 UP에서 자신이 생성한 RCtrl을 해제. 뒤따르는 Win·Shift UP까지 처리한 뒤 대기 복귀 |
| 중단 | 불완전한 순서, 합성 실패, 불확실한 수정 키 상태에서는 변환을 중단하고 복구 시도 |

이 표의 '판단'은 휴리스틱입니다. 원래 물리 Win·Shift·RCtrl을 함께 누르는 상황은 별도의 상태 소유권 처리가 필요하며, 첫 실험의 지원 대상으로 가정하지 않습니다. 실제 RCtrl을 누른 상태에서 합성 RCtrl UP을 보내면 사용자의 키 상태를 깨뜨릴 수 있으므로 단순히 모든 Ctrl을 해제하지 않습니다.

`SendInput`에 자체 표시값을 넣고 훅에서 재처리를 피하는 구조를 검토합니다. 이 값은 재귀 방지용이며 보안상 신뢰 증명은 아닙니다. 훅 내부에서 대기, 파일 쓰기, UI 처리를 하지 않고 이벤트 기반 버퍼와 타이머로 판별합니다.

### Raw Input과 훅의 역할

Raw Input은 입력 장치를 구분하는 진단에 사용합니다. `RIDEV_NOLEGACY`는 해당 앱의 레거시 입력 메시지를 제어하는 옵션이며, 다른 앱 전체에 대한 전역 차단 수단으로 취급하지 않습니다.

`WH_KEYBOARD_LL`은 입력 억제 후보지만 장치 핸들을 제공하지 않습니다. Raw Input과 훅 이벤트 간 일대일 대응이나 도착 순서를 보장한다고 가정하지 않습니다. 두 경로를 단순히 붙여 장치별 차단이 완성된다고 주장하지 않습니다.

### 중단·복구와 실험 완료 조건

정상 종료에서는 생성한 수정 키 상태를 추적해 해제하고 훅을 제거합니다. 강제 종료나 프로세스 충돌에서는 정리 코드 실행이 보장되지 않으므로 Ctrl 고착 방지가 해결됐다고 선언하지 않습니다. 훅은 타임아웃으로 조용히 제거될 수 있고, 입력 합성은 UIPI 제한을 받으므로 이 경우도 실기 검증 대상입니다.

다음 작업은 **시간 제한이 있는 관찰 실험 → 입력을 변경하지 않는 판별 실험 → 수동 실행 RCtrl 변환 실험** 순서입니다. Win/Shift 선행 입력, 실제 RCtrl 동시 입력, 다른 키보드 혼합, 빠른 Win 단축키에서의 오탐을 먼저 확인합니다. 이 단계가 통과되기 전에는 UI 확장이나 RAlt 지원을 시작하지 않습니다.
